이 페이지에서는 액세스 제어, 인증 및 자동화된 사용자 프로비저닝을 포함한 LangSmith의 사용자 관리 기능을 다룹니다:

- [액세스 제어 설정](#set-up-access-control): 역할 기반 액세스 제어(RBAC)를 구성하여 워크스페이스 내 사용자 권한을 관리하며, 사용자 정의 역할을 생성하고 사용자에게 할당합니다.
- [SAML SSO (엔터프라이즈 플랜)](#set-up-saml-sso-for-your-organization): SAML 2.0을 사용하여 엔터프라이즈 고객을 위한 Single Sign-On 인증을 설정하며, 주요 ID 공급자에 대한 구성을 포함합니다.
- [SCIM 사용자 프로비저닝 (엔터프라이즈 플랜)](#set-up-scim-for-your-organization): SCIM을 사용하여 ID 공급자와 LangSmith 간의 사용자 프로비저닝 및 프로비저닝 해제를 자동화합니다.

## 액세스 제어 설정하기

<Note>
RBAC(역할 기반 액세스 제어)는 엔터프라이즈 고객만 사용할 수 있는 기능입니다. 이 기능에 관심이 있으시면 [영업 팀에 문의](https://www.langchain.com/contact-sales)해 주세요. 다른 플랜은 모든 사용자에 대해 기본적으로 [`Admin` 역할](/langsmith/administration-overview)을 사용합니다.
</Note>

<Check>
액세스 제어를 설정하기 전에 [관리 개요](/langsmith/administration-overview) 페이지를 읽어보시면 도움이 될 것입니다.
</Check>

LangSmith는 RBAC를 사용하여 [워크스페이스](/langsmith/administration-overview#workspaces) 내 사용자 권한을 관리합니다. 이를 통해 누가 LangSmith 워크스페이스에 액세스할 수 있고 그 안에서 무엇을 할 수 있는지 제어할 수 있습니다. `workspace:manage` 권한을 가진 사용자만 워크스페이스의 액세스 제어 설정을 관리할 수 있습니다.

### 역할 생성하기

기본적으로 LangSmith는 다음과 같은 시스템 역할을 제공합니다:

- `Admin`: 워크스페이스 내 모든 리소스에 대한 전체 액세스 권한을 갖습니다.
- `Viewer`: 워크스페이스 내 모든 리소스에 대한 읽기 전용 액세스 권한을 갖습니다.
- `Editor`: 워크스페이스 관리(사용자 추가/제거, 역할 변경, 서비스 키 구성)를 제외한 모든 권한을 갖습니다.

이러한 역할이 귀하의 액세스 모델에 맞지 않는 경우, `Organization Admins`는 필요에 맞는 사용자 정의 역할을 생성할 수 있습니다.

역할을 생성하려면 [조직 설정 페이지](https://smith.langchain.com/settings)의 **Members and roles** 섹션에서 **Roles** 탭으로 이동합니다. 새로 생성하는 역할은 조직 내 모든 워크스페이스에서 사용할 수 있습니다.

**Create Role** 버튼을 클릭하여 새 역할을 생성합니다. **Create role** 양식이 열립니다.

![Create Role](/langsmith/images/create-role.png)

액세스를 제어하려는 다양한 LangSmith 리소스에 대한 권한을 할당합니다.

### 사용자에게 역할 할당하기

역할 설정이 완료되면 사용자에게 역할을 할당할 수 있습니다. 사용자에게 역할을 할당하려면 [조직 설정 페이지](https://smith.langchain.com/settings)의 `Workspaces` 섹션에서 `Workspace members` 탭으로 이동합니다.

각 사용자는 역할을 할당하는 데 사용할 수 있는 **Role** 드롭다운을 갖습니다.

![Assign Role](/langsmith/images/assign-role.png)

특정 역할을 가진 신규 사용자를 초대할 수도 있습니다.

![Invite User](/langsmith/images/invite-user.png)

## 조직에 SAML SSO 설정하기

Single Sign-On(SSO) 기능은 **엔터프라이즈 클라우드** 고객이 단일 인증 소스를 통해 LangSmith에 액세스할 수 있도록 합니다. 이를 통해 관리자는 팀 액세스를 중앙에서 관리하고 정보를 더욱 안전하게 보호할 수 있습니다.

LangSmith의 SSO 구성은 SAML(Security Assertion Markup Language) 2.0 표준을 사용하여 구축되었습니다. SAML 2.0은 ID 공급자(IdP)를 조직에 연결하여 더 쉽고 안전한 로그인 경험을 제공합니다.

SSO 서비스는 사용자가 하나의 자격 증명 세트(예: 이름 또는 이메일 주소와 비밀번호)를 사용하여 여러 애플리케이션에 액세스할 수 있도록 합니다. 서비스는 사용자에게 권한이 부여된 모든 애플리케이션에 대해 최종 사용자를 한 번만 인증하며, 사용자가 같은 세션 중에 애플리케이션을 전환할 때 추가 프롬프트를 제거합니다. SSO의 이점은 다음과 같습니다:

- 조직 소유자를 위해 여러 시스템에 걸친 사용자 관리를 간소화합니다.
- 조직이 자체 보안 정책(예: MFA)을 시행할 수 있도록 합니다.
- 최종 사용자가 여러 비밀번호를 기억하고 관리할 필요가 없습니다. 여러 애플리케이션에 걸쳐 하나의 액세스 지점에서 로그인할 수 있도록 하여 최종 사용자 경험을 단순화합니다.

### Just-in-time (JIT) 프로비저닝

LangSmith는 SAML SSO를 사용할 때 Just-in-time 프로비저닝을 지원합니다. 이를 통해 SAML SSO를 통해 로그인하는 사람이 자동으로 조직 및 선택된 워크스페이스에 구성원으로 참여할 수 있습니다.

<Note>
JIT 프로비저닝은 신규 사용자, 즉 [다른 로그인 방법](/langsmith/authentication-methods#cloud)을 통해 동일한 이메일 주소로 조직에 이미 액세스 권한이 없는 사용자에 대해서만 실행됩니다.
</Note>

### 로그인 방법 및 액세스

조직에 대한 SAML SSO 구성을 완료하면 사용자는 사용자 이름/비밀번호 또는 Google 인증과 같은 [다른 로그인 방법](/langsmith/authentication-methods#cloud) 외에도 SAML SSO를 통해 로그인할 수 있습니다:

- SAML SSO를 통해 로그인하면 사용자는 SAML SSO가 구성된 해당 조직에만 액세스할 수 있습니다.
- SAML SSO만을 로그인 방법으로 사용하는 사용자는 [개인 조직](/langsmith/administration-overview#organizations)을 갖지 않습니다.
- 다른 방법을 통해 로그인하면 사용자는 SAML SSO가 구성된 조직과 함께 자신이 속한 다른 조직에 액세스할 수 있습니다.

### SAML SSO만 강제하기

<Note>
SAML SSO만 강제하는 조직에서는 사용자 초대가 지원되지 않습니다. 초기 워크스페이스 멤버십 및 역할은 JIT 프로비저닝에 의해 결정되며, 이후 변경 사항은 UI에서 관리할 수 있습니다.
자동화된 사용자 관리의 추가 유연성을 위해 LangSmith는 SCIM을 지원합니다.
</Note>

사용자가 SAML SSO를 사용하여 로그인할 때만 조직에 액세스할 수 있도록 하려면 **Login via SSO only** 체크박스를 선택하고 **Save**를 클릭합니다. 이렇게 하면 비 SSO 로그인 방법을 통해 로그인한 조직 액세스 사용자는 SAML SSO를 사용하여 다시 로그인해야 합니다. 이 설정은 체크박스를 선택 해제하고 **Save**를 클릭하여 모든 로그인 방법을 허용하도록 다시 전환할 수 있습니다.

<Note>
이 설정을 `Only SAML SSO`로 업데이트하려면 SAML SSO를 통해 로그인해야 합니다. 이는 SAML 설정이 유효한지 확인하고 사용자가 조직에서 잠기는 것을 방지하기 위함입니다.
</Note>

문제 해결은 [SAML SSO FAQ](/langsmith/faq#saml-sso-faqs)를 참조하세요. SAML SSO 설정에 문제가 있으면 [support@langchain.dev](mailto:support@langchain.dev)로 LangChain 지원 팀에 문의하세요.

### 사전 요구 사항

<Note>
SAML SSO는 [엔터프라이즈 플랜](https://www.langchain.com/pricing-langsmith)의 조직에서 사용할 수 있습니다. 자세한 내용은 [영업팀에 문의](https://www.langchain.com/contact-sales)하세요.
</Note>

- 조직이 엔터프라이즈 플랜에 가입되어 있어야 합니다.
- ID 공급자(IdP)가 SAML 2.0 표준을 지원해야 합니다.
- [`Organization Admins`](/langsmith/observability-concepts#organization-roles)만 SAML SSO를 구성할 수 있습니다.

사용자 프로비저닝 및 프로비저닝 해제를 위해 SAML과 함께 SCIM을 사용하는 방법에 대한 지침은 [SCIM 설정](#set-up-scim-for-your-organization)을 참조하세요.

### 초기 구성

<Note>
IdP별 구성 단계는 다음 중 하나를 참조하세요:

- [Entra ID](#entra-id-azure)
- [Google](#google)
- [Okta](#okta)
</Note>

1. IdP에서: 다음 세부 정보로 SAML 애플리케이션을 구성한 다음 3단계를 위해 메타데이터 URL 또는 XML을 복사합니다.

   <Note>
   다음 URL은 미국 및 유럽 지역에서 다릅니다. 올바른 링크를 선택해야 합니다.
   </Note>

   1. Single sign-on URL (또는 ACS URL):
      - US: [https://auth.langchain.com/auth/v1/sso/saml/acs](https://auth.langchain.com/auth/v1/sso/saml/acs)
      - EU: [https://eu.auth.langchain.com/auth/v1/sso/saml/acs](https://eu.auth.langchain.com/auth/v1/sso/saml/acs)
   2. Audience URI (또는 SP Entity ID):
      - US: [https://auth.langchain.com/auth/v1/sso/saml/metadata](https://auth.langchain.com/auth/v1/sso/saml/metadata)
      - EU: [https://eu.auth.langchain.com/auth/v1/sso/saml/metadata](https://eu.auth.langchain.com/auth/v1/sso/saml/metadata)
   3. Name ID format: email address.
   4. Application username: email address.
   5. Required claims: `sub` 및 `email`.

2. LangSmith에서: **Settings** -> **Members and roles** -> **SSO Configuration**으로 이동합니다. 필수 정보를 입력하고 제출하여 SSO 로그인을 활성화합니다:

      1. `SAML metadata URL` 또는 `SAML metadata XML` 중 하나를 입력합니다.
      2. `Default workspace role` 및 `Default workspaces`를 선택합니다. SSO를 통해 로그인하는 신규 사용자는 선택된 역할로 지정된 워크스페이스에 추가됩니다.

- `Default workspace role` 및 `Default workspaces`는 편집할 수 있습니다. 업데이트된 설정은 신규 사용자에게만 적용되며 기존 사용자에게는 적용되지 않습니다.
- (곧 제공 예정) `SAML metadata URL` 및 `SAML metadata XML`은 편집할 수 있습니다. 이는 일반적으로 암호화 키가 순환/만료되거나 메타데이터 URL이 변경되었지만 동일한 IdP가 여전히 사용되는 경우에만 필요합니다.

### Entra ID (Azure)

추가 정보는 Microsoft의 [문서](https://learn.microsoft.com/en-us/entra/identity/enterprise-apps/add-application-portal-setup-sso)를 참조하세요.

<div id="create-application-entra-id"></div>
**1단계: 새 Entra ID 애플리케이션 통합 생성하기**

1. 권한이 있는 역할(예: `Global Administrator`)로 [Azure 포털](https://portal.azure.com/#home)에 로그인합니다. 왼쪽 탐색 창에서 `Entra ID` 서비스를 선택합니다.

2. **Enterprise Applications**으로 이동한 다음 **All Applications**을 선택합니다.

3. **Create your own application**을 클릭합니다.

4. **Create your own application** 창에서:

   1. 애플리케이션의 이름을 입력합니다(예: `LangSmith`).
   2. *Integrate any other application you don't find in the gallery (Non-gallery)**를 선택합니다.

5. **Create**를 클릭합니다.

**2단계: Entra ID 애플리케이션 구성 및 SAML 메타데이터 얻기**

1. 생성한 엔터프라이즈 애플리케이션을 엽니다.

2. 왼쪽 탐색 메뉴에서 **Manage** > **Single sign-on**을 선택합니다.

3. Single sign-on 페이지에서 **SAML**을 클릭합니다.

4. **Basic SAML Configuration**을 업데이트합니다:

   1. `Identifier (Entity ID)`:
      - US: [https://auth.langchain.com/auth/v1/sso/saml/metadata](https://auth.langchain.com/auth/v1/sso/saml/metadata)
      - EU: [https://eu.auth.langchain.com/auth/v1/sso/saml/metadata](https://eu.auth.langchain.com/auth/v1/sso/saml/metadata)
   2. `Reply URL (Assertion Consumer Service URL)`:
      - US: [https://auth.langchain.com/auth/v1/sso/saml/acs](https://auth.langchain.com/auth/v1/sso/saml/acs)
      - EU: [https://eu.auth.langchain.com/auth/v1/sso/saml/acs](https://eu.auth.langchain.com/auth/v1/sso/saml/acs)
   3. `Relay State`, `Logout Url` 및 `Sign on URL`은 비워 둡니다.
   4. **Save**를 클릭합니다.

5. 필수 클레임이 **Namespace**: `http://schemas.xmlsoap.org/ws/2005/05/identity/claims`와 함께 있는지 확인합니다:

   1. `sub`: `user.objectid`.
   2. `emailaddress`: `user.userprincipalname` 또는 `user.mail` (후자를 사용하는 경우 모든 사용자가 `Contact Information` 아래 `Email` 필드를 채웠는지 확인합니다).
   3. (선택 사항) SCIM의 경우 `Unique User Identifier (Name ID)`에 대한 구체적인 지침은 [설정 문서](/langsmith/user-management)를 참조하세요.

6. SAML 기반 Sign-on 페이지의 **SAML Certificates** 아래에서 **App Federation Metadata URL**을 복사합니다.

**3단계: LangSmith SSO 구성 설정하기**

이전 단계의 메타데이터 URL을 사용하여 [초기 구성](#initial-configuration)의 `필수 정보 입력` 단계에 있는 지침을 따릅니다.

**4단계: SSO 설정 확인하기**

1. Entra ID의 사용자/그룹에 애플리케이션을 할당합니다:

   1. **Manage** > **Users and groups**를 선택합니다.

   2. **Add user/group**을 클릭합니다.

   3. **Add Assignment** 창에서:

      1. **Users** 아래에서 **None Selected**를 클릭합니다.
      2. 엔터프라이즈 애플리케이션에 할당하려는 사용자를 검색한 다음 **Select**를 클릭합니다.
      3. 사용자가 선택되었는지 확인하고 **Assign**을 클릭합니다.

2. **SSO Configuration** 페이지의 고유 로그인 URL을 통해 사용자가 로그인하도록 하거나 **Manage** > **Single sign-on**으로 이동하여 **Test single sign-on with (application name)**를 선택합니다.

### Google

추가 정보는 Google의 [문서](https://support.google.com/a/answer/6087519)를 참조하세요.

**1단계: Google Workspace SAML 애플리케이션 생성 및 구성하기**

1. 적절한 권한이 있는 관리자 계정으로 로그인되어 있는지 확인합니다.

2. Admin console에서 **Menu** -> **Apps** -> **Web and mobile apps**로 이동합니다.

3. **Add App**을 클릭한 다음 **Add custom SAML app**을 클릭합니다.

4. 앱 이름을 입력하고 선택적으로 아이콘을 업로드합니다. **Continue**를 클릭합니다.

5. Google Identity Provider details 페이지에서 **IDP metadata**를 다운로드하고 2단계를 위해 저장합니다. **Continue**를 클릭합니다.

6. `Service Provider Details` 창에서 다음을 입력합니다:

   1. `ACS URL`:
      - US: [https://auth.langchain.com/auth/v1/sso/saml/acs](https://auth.langchain.com/auth/v1/sso/saml/acs)
      - EU: [https://eu.auth.langchain.com/auth/v1/sso/saml/acs](https://eu.auth.langchain.com/auth/v1/sso/saml/acs)
   2. `Entity ID`:
      - US: [https://auth.langchain.com/auth/v1/sso/saml/metadata](https://auth.langchain.com/auth/v1/sso/saml/metadata)
      - EU: [https://eu.auth.langchain.com/auth/v1/sso/saml/metadata](https://eu.auth.langchain.com/auth/v1/sso/saml/metadata)
   3. `Start URL` 및 `Signed response` 박스는 비워 둡니다.
   4. `Name ID` 형식을 `EMAIL`로 설정하고 `Name ID`를 기본값(`Basic Information > Primary email`)으로 둡니다.
   5. `Continue`를 클릭합니다.

7. `Add mapping`을 사용하여 필수 클레임이 있는지 확인합니다:
   1. `Basic Information > Primary email` -> `email`

**2단계: LangSmith SSO 구성 설정하기**

## 조직에 SCIM 설정하기

System for Cross-domain Identity Management(SCIM)는 사용자 프로비저닝 자동화를 허용하는 개방형 표준입니다. SCIM을 사용하면 LangSmith [조직 및 워크스페이스](/langsmith/administration-overview)에서 사용자를 자동으로 프로비저닝 및 프로비저닝 해제하여 조직의 ID 공급자와 사용자 액세스를 동기화할 수 있습니다.

<Note>
SCIM은 [엔터프라이즈 플랜](https://www.langchain.com/pricing)의 조직에서 사용할 수 있습니다. 자세한 내용은 [영업팀에 문의](https://www.langchain.com/contact-sales)하세요.

SCIM은 Helm 차트 버전 0.10.41(애플리케이션 버전 0.10.108) 이상에서 사용할 수 있습니다.

SCIM 지원은 API 전용입니다(아래 지침 참조).
</Note>

SCIM은 수동 사용자 관리의 필요성을 제거하고 사용자 액세스가 항상 조직의 ID 시스템과 최신 상태를 유지하도록 보장합니다. 이를 통해 다음이 가능합니다:

- **자동화된 사용자 관리**: IdP의 상태에 따라 LangSmith에서 사용자가 자동으로 추가, 업데이트 및 제거됩니다.
- **관리 오버헤드 감소**: 여러 시스템에서 수동으로 사용자 액세스를 관리할 필요가 없습니다.
- **보안 향상**: 조직을 떠나는 사용자는 LangSmith에서 자동으로 프로비저닝 해제됩니다.
- **일관된 액세스 제어**: 사용자 속성 및 그룹 멤버십이 시스템 간에 동기화됩니다.
- **팀 액세스 제어 확장**: 많은 워크스페이스 및 사용자 정의 역할을 가진 대규모 팀을 효율적으로 관리합니다.
- **역할 할당**: 사용자 그룹에 대해 특정 [조직 역할](/langsmith/observability-concepts#organization-roles) 및 [워크스페이스 역할](/langsmith/observability-concepts#workspace-roles)을 선택합니다.

### 요구 사항

#### 사전 요구 사항

- 조직이 엔터프라이즈 플랜에 가입되어 있어야 합니다.
- ID 공급자(IdP)가 SCIM 2.0을 지원해야 합니다.
- [조직 관리자](/langsmith/administration-overview#organization-roles)만 SCIM을 구성할 수 있습니다.
- 클라우드 고객의 경우: 조직에 대해 [SAML SSO](#set-up-saml-sso-for-your-organization)를 구성할 수 있어야 합니다.
- 자체 호스팅 고객의 경우: [Client Secret을 사용한 OAuth](/langsmith/self-host-sso#with-secret) 인증 모드가 활성화되어 있어야 합니다.
- 자체 호스팅 고객의 경우 ID 공급자에서 LangSmith로의 네트워크 트래픽이 허용되어야 합니다:
  - Microsoft Entra ID는 IP 범위 허용 목록 또는 에이전트 기반 솔루션을 지원하여 연결을 제공합니다.
    ([세부 정보](https://learn.microsoft.com/en-us/entra/identity/app-provisioning/use-scim-to-provision-users-and-groups#ip-ranges)).
  - Okta는 IP 또는 도메인 허용 목록 지정([세부 정보](https://help.okta.com/en-us/content/topics/security/ip-address-allow-listing.htm))
    또는 에이전트 기반 솔루션([세부 정보](https://help.okta.com/en-us/content/topics/provisioning/opp/opp-main.htm))을 지원하여 연결을 제공합니다.

#### 역할 우선순위

사용자가 동일한 워크스페이스에 대해 여러 그룹에 속할 때 다음 우선순위가 적용됩니다:

1. **조직 관리자 그룹**이 가장 높은 우선순위를 갖습니다. 이 그룹의 사용자는 모든 워크스페이스에서 `Admin`이 됩니다.
2. **가장 최근에 생성된 워크스페이스별 그룹**이 다른 워크스페이스 그룹보다 우선합니다.

<Note>
그룹이 삭제되거나 사용자가 그룹에서 제거되면 우선순위 규칙에 따라 남아 있는 그룹 멤버십에 따라 액세스가 업데이트됩니다.

SCIM 그룹 멤버십은 수동으로 할당된 역할 또는 Just-in-time (JIT) 프로비저닝을 통해 할당된 역할을 재정의합니다. 충돌을 방지하려면 JIT 프로비저닝을 비활성화하는 것이 좋습니다.
</Note>

#### 이메일 확인

클라우드에서만 SCIM으로 새 사용자를 생성하면 사용자에게 이메일이 전송됩니다.
이 이메일의 링크를 클릭하여 이메일 주소를 확인해야 합니다.
링크는 24시간 후에 만료되며, SCIM을 통해 사용자를 제거하고 다시 추가하여 필요한 경우 다시 보낼 수 있습니다.

### 속성 및 매핑

#### 그룹 명명 규칙

그룹 멤버십은 특정 명명 규칙을 사용하여 LangSmith 워크스페이스 멤버십 및 워크스페이스 역할에 매핑됩니다:

**조직 관리자 그룹**

형식: `<optional_prefix>Organization Admin` 또는 `<optional_prefix>Organization Admins`

예:

- `LS:Organization Admins`
- `Groups-Organization Admins`
- `Organization Admin`

**워크스페이스별 그룹**

형식: `<optional_prefix><org_role_name>:<workspace_name>:<workspace_role_name>`

예:

- `LS:Organization User:Production:Annotators`
- `Groups-Organization User:Engineering:Developers`
- `Organization User:Marketing:Viewers`

### 매핑

ID 공급자에 따라 구체적인 지침이 다를 수 있지만, 이러한 매핑은 LangSmith SCIM 통합에서 지원되는 내용을 보여줍니다:

#### 사용자 속성

| **LangSmith 앱 속성**    | **ID 공급자 속성**                       | **매칭 우선순위** |
| ------------------------------ | ----------------------------------------------------- | ----------------------- |
| `userName`<sup>1</sup>         | email address                                         |                         |
| `active`                       | `!deactivated`                                        |                         |
| `emails[type eq "work"].value` | email address<sup>2</sup>                             |                         |
| `name.formatted`               | `displayName` OR `givenName + familyName`<sup>3</sup> |                         |
| `givenName`                    | `givenName`                                           |                         |
| `familyName`                   | `familyName`                                          |                         |
| `externalId`                   | `sub`<sup>4</sup>                                     | 1                       |

1. `userName`은 LangSmith에서 필수가 아닙니다.
2. 이메일 주소는 필수입니다.
3. `displayName`이 `Firstname Lastname` 형식과 일치하지 않는 경우 계산된 표현식을 사용합니다.
4. 불일치를 방지하기 위해 클라우드 고객의 경우 SAML `NameID` 어설션과 일치해야 하고, 자체 호스팅의 경우 `sub` OAuth2.0 클레임과 일치해야 합니다.

#### 그룹 속성

| **LangSmith 앱 속성** | **ID 공급자 속성** | **매칭 우선순위** |
| --------------------------- | ------------------------------- | ----------------------- |
| `displayName`               | `displayName`<sup>1</sup>       | 1                       |
| `externalId`                | `objectId`                      |                         |
| `members`                   | `members`                       |                         |

1. 그룹은 [그룹 명명 규칙](#group-naming-convention) 섹션에 설명된 명명 규칙을 따라야 합니다.
   회사에 그룹 명명 정책이 있는 경우 대신 `description` ID 공급자 속성에서 매핑하고
   [그룹 명명 규칙](#group-naming-convention) 섹션을 기반으로 설명을 설정해야 합니다.

### 1단계 - SAML SSO 구성 (클라우드 전용)

[SAML SSO](#set-up-saml-sso-for-your-organization) 구성에는 두 가지 시나리오가 있습니다:

1. 조직에 대해 SAML SSO가 이미 구성된 경우, 애플리케이션을 처음 추가하는 단계([Okta Integration Network에서 애플리케이션 추가](#add-application-okta-oin) 또는 [새 Entra ID 애플리케이션 통합 생성](#create-application-entra-id))를 건너뛰어야 합니다. 이미 애플리케이션이 구성되어 있으므로 프로비저닝만 활성화하면 됩니다.
2. SCIM과 함께 SAML SSO를 처음 구성하는 경우 먼저 [SAML SSO 설정](#set-up-saml-sso-for-your-organization) 지침을 따른 _다음_ 여기의 지침에 따라 SCIM을 활성화합니다.

#### NameID 형식

LangSmith는 SAML NameID를 사용하여 사용자를 식별합니다. NameID는 SAML 응답의 필수 필드이며 대소문자를 구분하지 않습니다.

NameID는 다음을 충족해야 합니다:

1. 각 사용자에게 고유해야 합니다.
2. 무작위로 생성된 고유 사용자 ID와 같이 절대 변경되지 않는 영구 값이어야 합니다.
3. 각 로그인 시도 시 정확히 일치해야 합니다. 사용자 입력에 의존해서는 안 됩니다.

NameID는 이메일 주소나 사용자 이름이 시간이 지남에 따라 변경될 가능성이 더 높고 대소문자를 구분할 수 있으므로 이메일 주소나 사용자 이름이 아니어야 합니다.

NameID 형식은 이메일과 같이 다른 형식이 필요한 필드를 사용하지 않는 한 `Persistent`여야 합니다.

### 2단계 - JIT 프로비저닝 비활성화

SCIM을 활성화하기 전에 자동 및 수동 사용자 프로비저닝 간의 충돌을 방지하기 위해 [Just-in-time (JIT) 프로비저닝](/langsmith/user-management#just-in-time-jit-provisioning)을 비활성화합니다.

#### 클라우드에서 JIT 비활성화

`PATCH /orgs/current/info` [엔드포인트](https://api.smith.langchain.com/redoc#tag/orgs/operation/update_current_organization_info_api_v1_orgs_current_info_patch)를 사용합니다:

```bash
curl -X PATCH $LANGCHAIN_ENDPOINT/orgs/current/info \
  -H "X-Api-Key: $LANGCHAIN_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"jit_provisioning_enabled": false}'
```

#### 자체 호스팅에서 JIT 비활성화

LangSmith 차트 버전 **0.11.14**부터 SSO를 사용하는 자체 호스팅 조직에 대해 JIT 프로비저닝을 비활성화할 수 있습니다. 비활성화하려면 다음 값을 설정합니다:

```yaml
commonEnv:
  - name: SELF_HOSTED_JIT_PROVISIONING_ENABLED
    value: "false"
```

### 3단계 - SCIM Bearer Token 생성

<Note>
자체 호스팅 환경에서 아래의 전체 URL은 `https://langsmith.yourdomain.com/api/v1/platform/orgs/current/scim/tokens`(하위 도메인 없이, `/api/v1` 경로 접두사 참고) 또는 `https://langsmith.yourdomain.com/subdomain/api/v1/platform/orgs/current/scim/tokens`(하위 도메인 포함)처럼 보일 수 있습니다. 자세한 내용은 [ingress 문서](/langsmith/self-host-ingress)를 참조하세요.
</Note>

조직을 위한 SCIM Bearer Token을 생성합니다. 이 토큰은 IdP가 SCIM API 요청을 인증하는 데 사용됩니다. 환경 변수가 적절하게 설정되어 있는지 확인합니다. 예:

```bash
curl -X POST $LANGCHAIN_ENDPOINT/v1/platform/orgs/current/scim/tokens \
  -H "X-Api-Key: $LANGCHAIN_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"description": "Your description here"}'
```

SCIM Bearer Token 값은 이 요청에 대한 응답 외부에서는 사용할 수 없습니다. 다음 추가 엔드포인트가 있습니다:

- `GET /v1/platform/orgs/current/scim/tokens`
- `GET /v1/platform/orgs/current/scim/tokens/{scim_token_id}`
- `PATCH /v1/platform/orgs/current/scim/tokens/{scim_token_id}` (`description` 필드만 지원됨)
- `DELETE /v1/platform/orgs/current/scim/tokens/{scim_token_id}`

### 4단계 - ID 공급자 구성

<Note>
Azure Entra ID(이전 Azure AD) 또는 Okta를 사용하는 경우 ID 공급자 설정에 대한 구체적인 지침이 있습니다([Azure Entra ID](#azure-entra-id-configuration-steps), [Okta](#okta) 참조). 위의 요구 사항 및 단계는 모든 ID 공급자에 적용됩니다.
</Note>

#### Azure Entra ID 구성 단계

추가 정보는 Microsoft의 [문서](https://learn.microsoft.com/en-us/entra/identity/app-provisioning/user-provisioning)를 참조하세요.

<Note>
자체 호스팅 설치에서는 `oid` JWT 클레임이 `sub`로 사용됩니다.
추가 세부 정보는 [이 Microsoft Learn 링크](https://learn.microsoft.com/en-us/answers/questions/5546297/how-to-link-oidc-users-with-scim)
및 [관련 구성 지침](/langsmith/self-host-sso#override-sub-claim)을 참조하세요.
</Note>

**1단계: 엔터프라이즈 애플리케이션에서 SCIM 구성하기**

1. 권한이 있는 역할(예: `Global Administrator`)로 [Azure 포털](https://portal.azure.com/#home)에 로그인합니다.
2. 기존 LangSmith 엔터프라이즈 애플리케이션으로 이동합니다.
3. 왼쪽 탐색 메뉴에서 **Manage** > **Provisioning**을 선택합니다.
4. **Get started**를 클릭합니다.

**2단계: 관리자 자격 증명 구성하기**

1. **Admin Credentials** 아래:

   - **Tenant URL**:

     - US: `https://api.smith.langchain.com/scim/v2`
     - EU: `https://eu.api.smith.langchain.com/scim/v2`
     - Self-hosted: `<langsmith_url>/scim/v2`

   - **Secret Token**: 3단계에서 생성한 SCIM Bearer Token을 입력합니다.

2. **Test Connection**을 클릭하여 구성을 확인합니다.

3. **Save**를 클릭합니다.

**3단계: 속성 매핑 구성하기**

`Mappings` 아래에서 다음 속성 매핑을 구성합니다:

**사용자 속성**

**Target Object Actions**를 `Create` 및 `Update`로 설정합니다(안전을 위해 `Delete`를 비활성화한 상태로 시작):

| **LangSmith 앱 속성**    | **Microsoft Entra ID 속성**                      | **매칭 우선순위** |
| :-----------------------------: | :----------------------------------------------------: | :----------------------: |
| `userName`                     | `userPrincipalName`                                   |                         |
| `active`                       | `Not([IsSoftDeleted])`                                |                         |
| `emails[type eq "work"].value` | `mail`1                                               |                         |
| `name.formatted`               | `displayName` OR `Join(" ", [givenName], [surname])`2 |                         |
| `externalId`                   | `objectId`3                                           | 1                       |

1. 사용자의 이메일 주소는 Entra ID에 있어야 합니다.
2. `displayName`이 `Firstname Lastname` 형식과 일치하지 않는 경우 `Join` 표현식을 사용합니다.
3. 불일치를 방지하기 위해 SAML NameID 어설션 및 `sub` OAuth2.0 클레임과 일치해야 합니다. 클라우드의 SAML SSO의 경우 `Unique User Identifier (Name ID)` 필수 클레임은 `user.objectID`여야 하며 `Name identifier format`은 `persistent`여야 합니다.

**그룹 속성**

**Target Object Actions**를 `Create` 및 `Update`만으로 설정합니다(안전을 위해 `Delete`를 비활성화한 상태로 시작):

| **LangSmith 앱 속성** | **Microsoft Entra ID 속성** | **매칭 우선순위** |
| :-------------------------: | :-------------------------------: | :----------------------: |
| `displayName`               | `displayName`1                   | 1                       |
| `externalId`                | `objectId`                       |                         |
| `members`                   | `members`                        |                         |

1. 그룹은 [그룹 명명 규칙](#group-naming-convention) 섹션에 설명된 명명 규칙을 따라야 합니다.
   회사에 그룹 명명 정책이 있는 경우 대신 `description` Microsoft Entra ID 속성에서 매핑하고
   [그룹 명명 규칙](#group-naming-convention) 섹션을 기반으로 설명을 설정해야 합니다.

**4단계: 사용자 및 그룹 할당하기**

1. **Applications** > **Applications**에서 LangSmith 엔터프라이즈 애플리케이션을 선택합니다.
2. **Assignments** 탭에서 **Assign**을 클릭한 다음 **Assign to People** 또는 **Assign to Groups**를 클릭합니다.
3. 원하는 항목을 선택한 다음 **Assign** 및 **Done**을 클릭합니다.

**5단계: 프로비저닝 활성화하기**

1. **Provisioning** 아래에서 **Provisioning Status**를 `On`으로 설정합니다.
2. 초기 동기화를 모니터링하여 사용자 및 그룹이 올바르게 프로비저닝되었는지 확인합니다.
3. 확인되면 사용자 및 그룹 매핑 모두에 대해 `Delete` 작업을 활성화합니다.

문제 해결은 [SAML SSO FAQ](/langsmith/faq#saml-sso-faqs)를 참조하세요. SCIM 설정에 문제가 있으면 [support@langchain.dev](mailto:support@langchain.dev)로 LangChain 지원 팀에 문의하세요.

</Note>

<div id="add-application-okta-oin">
    <b>1단계: Okta Integration Network에서 애플리케이션 추가하기</b>
</div>

<Note>
SAML(클라우드) 또는 OIDC가 있는 OAuth2.0(자체 호스팅)을 통해 SSO 로그인을 이미 구성한 경우 이 단계를 건너뜁니다.
</Note>

클라우드의 경우 [SAML SSO 설정](#okta) 또는 자체 호스팅의 경우 [OAuth2.0 설정](/langsmith/self-host-sso#okta-idp-setup)을 참조하세요.

**2단계: API 통합 구성하기**

1. General 탭에서 [1단계](#add-application-okta-oin)의 지침에 따라 `LangSmithUrl`이 입력되었는지 확인합니다.
1. Provisioning 탭에서 `Integration`을 선택합니다.
1. `Edit`을 선택한 다음 `Enable API integration`을 선택합니다.
1. API Token의 경우 [위에서 생성한](#step-3-generate-scim-bearer-token) SCIM 토큰을 붙여넣습니다.
1. `Import Groups`를 선택한 상태로 유지합니다.
1. 구성을 확인하려면 Test API Credentials를 선택합니다.
1. Save를 선택합니다.
1. API 통합 세부 정보를 저장한 후 왼쪽에 새 설정 탭이 나타납니다. `To App`을 선택합니다.
1. Edit을 선택합니다.
1. Create Users, Update Users 및 Deactivate Users에 대해 Enable 체크박스를 선택합니다.
1. Save를 선택합니다.
1. Assignments 탭에서 사용자 및/또는 그룹을 할당합니다. 할당된 사용자는 LangSmith 그룹에서 생성되고 관리됩니다.

**3단계: 사용자 프로비저닝 설정 구성하기**

1. 프로비저닝 구성: `Provisioning > To App > Provisioning to App`에서 `Edit`을 클릭한 다음 `Create Users`, `Update User Attributes` 및 `Deactivate Users`를 선택합니다.
1. `<application_name> Attribute Mappings`에서 아래와 같이 사용자 속성 매핑을 설정하고 나머지는 삭제합니다:

![SCIM Okta User Attributes Mapping](/langsmith/images/scim_okta_user_attributes.png)

**4단계: 그룹 푸시하기**

<Note>
Okta는 그룹 이름 자체 외에는 그룹 속성을 지원하지 않으므로 그룹 이름은 [그룹 명명 규칙](#group-naming-convention) 섹션에 설명된 명명 규칙을 _반드시_ 따라야 합니다.
</Note>

Okta의 [Enable Group Push](https://help.okta.com/en-us/content/topics/users-groups-profiles/usgp-enable-group-push.htm) 지침에 따라 이름 또는 규칙별로 푸시할 그룹을 구성합니다.

다른 ID 공급자는 테스트되지 않았지만 SCIM 구현에 따라 작동할 수 있습니다.
