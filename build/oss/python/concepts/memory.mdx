[Memory](/oss/python/langgraph/add-memory)는 이전 상호작용에 대한 정보를 기억하는 시스템입니다. AI agent에게 메모리는 이전 상호작용을 기억하고, 피드백으로부터 학습하며, 사용자 선호도에 적응할 수 있게 해주기 때문에 매우 중요합니다. Agent가 수많은 사용자 상호작용을 포함하는 더 복잡한 작업을 처리함에 따라, 이러한 기능은 효율성과 사용자 만족도 모두에 필수적이 됩니다.

이 개념 가이드는 회상 범위에 따른 두 가지 유형의 메모리를 다룹니다:

* [Short-term memory](#short-term-memory), 또는 [thread](/oss/python/langgraph/persistence#threads) 범위 메모리는 세션 내에서 메시지 기록을 유지하여 진행 중인 대화를 추적합니다. LangGraph는 short-term memory를 agent의 [state](/oss/python/langgraph/graph-api#state)의 일부로 관리합니다. State는 [checkpointer](/oss/python/langgraph/persistence#checkpoints)를 사용하여 데이터베이스에 지속되므로 thread는 언제든지 재개할 수 있습니다. Short-term memory는 graph가 호출되거나 step이 완료될 때 업데이트되며, State는 각 step 시작 시 읽힙니다.
* [Long-term memory](#long-term-memory)는 세션 간에 사용자별 또는 애플리케이션 수준 데이터를 저장하며, 대화 thread _간에_ 공유됩니다. _언제든지_ 그리고 _어떤 thread에서든_ 회상할 수 있습니다. 메모리는 단일 thread ID 내가 아니라 모든 사용자 정의 namespace로 범위가 지정됩니다. LangGraph는 장기 메모리를 저장하고 회상할 수 있도록 [stores](/oss/python/langgraph/persistence#memory-store) ([참조 문서](https://langchain-ai.github.io/langgraph/reference/store/#langgraph.store.base.BaseStore))를 제공합니다.

![](/oss/images/short-vs-long.png)

## Short-term memory

[Short-term memory](/oss/python/langgraph/add-memory#add-short-term-memory)는 애플리케이션이 단일 [thread](/oss/python/langgraph/persistence#threads) 또는 대화 내에서 이전 상호작용을 기억할 수 있게 해줍니다. [Thread](/oss/python/langgraph/persistence#threads)는 이메일이 단일 대화에서 메시지를 그룹화하는 방식과 유사하게 세션에서 여러 상호작용을 구성합니다.

LangGraph는 short-term memory를 thread 범위 checkpoint를 통해 지속되는 agent의 state의 일부로 관리합니다. 이 state는 일반적으로 업로드된 파일, 검색된 문서 또는 생성된 아티팩트와 같은 다른 상태 데이터와 함께 대화 기록을 포함할 수 있습니다. 이를 graph의 state에 저장함으로써, 봇은 서로 다른 thread 간의 분리를 유지하면서 특정 대화의 전체 context에 접근할 수 있습니다.

### Manage short-term memory

대화 기록은 short-term memory의 가장 일반적인 형태이며, 긴 대화는 오늘날의 LLM에 어려움을 제기합니다. 전체 기록이 LLM의 context window에 맞지 않으면 복구할 수 없는 오류가 발생할 수 있습니다. LLM이 전체 context 길이를 지원하더라도, 대부분의 LLM은 긴 context에서 여전히 성능이 떨어집니다. 오래되거나 주제를 벗어난 내용에 "주의가 산만해지며", 응답 시간이 느려지고 비용이 증가합니다.

Chat model은 개발자가 제공한 지침(system message)과 사용자 입력(human messages)을 포함하는 message를 사용하여 context를 수용합니다. Chat 애플리케이션에서 message는 사람의 입력과 모델 응답 사이를 번갈아 가며, 시간이 지남에 따라 점점 더 길어지는 message 목록을 생성합니다. Context window가 제한되어 있고 토큰이 많은 message 목록이 비용이 많이 들 수 있기 때문에, 많은 애플리케이션이 오래된 정보를 수동으로 제거하거나 잊어버리는 기법을 사용하면 이점을 얻을 수 있습니다.

![](/oss/images/filter.png)

메시지 관리를 위한 일반적인 기법에 대한 자세한 내용은 [Add and manage memory](/oss/python/langgraph/add-memory#manage-short-term-memory) 가이드를 참조하세요.

## Long-term memory

LangGraph의 [Long-term memory](/oss/python/langgraph/add-memory#add-long-term-memory)는 시스템이 서로 다른 대화 또는 세션 간에 정보를 유지할 수 있게 해줍니다. **Thread 범위**인 short-term memory와 달리, long-term memory는 사용자 정의 "namespace" 내에 저장됩니다.

Long-term memory는 만능 솔루션이 없는 복잡한 과제입니다. 그러나 다음 질문들은 서로 다른 기법을 탐색하는 데 도움이 되는 프레임워크를 제공합니다:

* [메모리의 유형은 무엇인가?](#memory-types) 인간은 사실을 기억하고([semantic memory](#semantic-memory)), 경험을 기억하며([episodic memory](#episodic-memory)), 규칙을 기억하는([procedural memory](#procedural-memory)) 데 메모리를 사용합니다. AI agent도 같은 방식으로 메모리를 사용할 수 있습니다. 예를 들어, AI agent는 작업을 수행하기 위해 사용자에 대한 특정 사실을 기억하는 데 메모리를 사용할 수 있습니다.
* [언제 메모리를 업데이트하고 싶은가?](#writing-memories) 메모리는 agent의 애플리케이션 로직의 일부로 업데이트될 수 있습니다(예: "hot path에서"). 이 경우 agent는 일반적으로 사용자에게 응답하기 전에 사실을 기억하기로 결정합니다. 또는 메모리는 백그라운드 작업(백그라운드/비동기적으로 실행되며 메모리를 생성하는 로직)으로 업데이트될 수 있습니다. [아래 섹션](#writing-memories)에서 이러한 접근 방식 간의 트레이드오프를 설명합니다.

### Memory types

서로 다른 애플리케이션은 다양한 유형의 메모리가 필요합니다. 비유가 완벽하지는 않지만, [인간 메모리 유형](https://www.psychologytoday.com/us/basics/memory/types-of-memory?ref=blog.langchain.dev)을 살펴보는 것이 통찰력을 줄 수 있습니다. 일부 연구(예: [CoALA 논문](https://arxiv.org/pdf/2309.02427))는 이러한 인간 메모리 유형을 AI agent에서 사용되는 것과 매핑하기도 했습니다.

| 메모리 유형 | 저장되는 것 | 인간의 예 | Agent의 예 |
|-------------|----------------|---------------|---------------|
| [Semantic](#semantic-memory) | 사실 | 학교에서 배운 것들 | 사용자에 대한 사실 |
| [Episodic](#episodic-memory) | 경험 | 내가 한 일들 | 과거 agent 행동 |
| [Procedural](#procedural-memory) | 지침 | 본능이나 운동 기술 | Agent 시스템 프롬프트 |

#### Semantic memory

인간과 AI agent 모두에서 [Semantic memory](https://en.wikipedia.org/wiki/Semantic_memory)는 특정 사실과 개념의 보유를 포함합니다. 인간의 경우, 학교에서 배운 정보와 개념 및 그 관계에 대한 이해를 포함할 수 있습니다. AI agent의 경우, semantic memory는 종종 과거 상호작용의 사실이나 개념을 기억하여 애플리케이션을 개인화하는 데 사용됩니다.

<Note>
Semantic memory는 "semantic search"와 다릅니다. Semantic search는 "의미"(일반적으로 임베딩)를 사용하여 유사한 콘텐츠를 찾는 기법입니다. Semantic memory는 심리학 용어로 사실과 지식을 저장하는 것을 의미하며, semantic search는 정확한 일치가 아닌 의미를 기반으로 정보를 검색하는 방법입니다.
</Note>

##### Profile

Semantic memory는 다양한 방식으로 관리될 수 있습니다. 예를 들어, 메모리는 사용자, 조직 또는 다른 엔티티(agent 자체 포함)에 대한 잘 범위가 지정되고 구체적인 정보의 단일하고 지속적으로 업데이트되는 "profile"이 될 수 있습니다. Profile은 일반적으로 도메인을 나타내기 위해 선택한 다양한 키-값 쌍을 가진 JSON 문서입니다.

Profile을 기억할 때는 매번 profile을 **업데이트**하고 있는지 확인해야 합니다. 결과적으로 이전 profile을 전달하고 [모델에게 새 profile을 생성하도록](https://github.com/langchain-ai/memory-template) 요청하거나 (또는 이전 profile에 적용할 일부 [JSON patch](https://github.com/hinthornw/trustcall)) 해야 합니다. Profile이 커질수록 오류가 발생하기 쉬우며, profile을 여러 문서로 분할하거나 메모리 스키마가 유효하게 유지되도록 문서를 생성할 때 **엄격한** 디코딩을 사용하면 이점을 얻을 수 있습니다.

##### Collection

또는 메모리는 시간이 지남에 따라 지속적으로 업데이트되고 확장되는 문서 컬렉션이 될 수 있습니다. 각 개별 메모리는 더 좁게 범위가 지정되고 생성하기 쉬울 수 있으므로, 시간이 지나도 정보를 **잃을** 가능성이 적습니다. LLM이 새 정보를 기존 profile과 조정하는 것보다 새 정보에 대한 _새_ 객체를 생성하는 것이 더 쉽습니다. 결과적으로 문서 컬렉션은 [다운스트림에서 더 높은 recall](https://en.wikipedia.org/wiki/Precision_and_recall)로 이어지는 경향이 있습니다.

그러나 이는 메모리 업데이트에 약간의 복잡성을 이전합니다. 이제 모델은 목록의 기존 항목을 _삭제_하거나 _업데이트_해야 하며, 이는 까다로울 수 있습니다. 또한 일부 모델은 과도하게 삽입하는 경향이 있고 다른 모델은 과도하게 업데이트하는 경향이 있을 수 있습니다. 이를 관리하는 한 가지 방법은 [Trustcall](https://github.com/hinthornw/trustcall) 패키지를 참조하고, 동작을 조정하는 데 도움이 되도록 평가([LangSmith](https://docs.smith.langchain.com/tutorials/Developers/evaluation)와 같은 도구 사용)를 고려하세요.

문서 컬렉션 작업은 또한 목록에 대한 메모리 **검색**에 복잡성을 이전합니다. `Store`는 현재 [semantic search](https://langchain-ai.github.io/langgraph/reference/store/#langgraph.store.base.SearchOp.query)와 [콘텐츠별 필터링](https://langchain-ai.github.io/langgraph/reference/store/#langgraph.store.base.SearchOp.filter)을 모두 지원합니다.

마지막으로, 메모리 컬렉션을 사용하면 모델에 포괄적인 context를 제공하는 것이 어려울 수 있습니다. 개별 메모리가 특정 스키마를 따를 수 있지만, 이 구조는 메모리 간의 전체 context나 관계를 캡처하지 못할 수 있습니다. 결과적으로 이러한 메모리를 사용하여 응답을 생성할 때, 모델은 통합된 profile 접근 방식에서 더 쉽게 사용할 수 있는 중요한 context 정보가 부족할 수 있습니다.

![](/oss/images/update-list.png)

메모리 관리 접근 방식과 관계없이, 핵심은 agent가 semantic memory를 사용하여 [응답을 근거짓기](/oss/python/langchain/retrieval)하며, 이는 종종 더 개인화되고 관련성 있는 상호작용으로 이어진다는 것입니다.

#### Episodic memory

인간과 AI agent 모두에서 [Episodic memory](https://en.wikipedia.org/wiki/Episodic_memory)는 과거 사건이나 행동을 회상하는 것을 포함합니다. [CoALA 논문](https://arxiv.org/pdf/2309.02427)은 이를 잘 설명합니다: 사실은 semantic memory에 기록될 수 있지만, *경험*은 episodic memory에 기록될 수 있습니다. AI agent의 경우, episodic memory는 종종 agent가 작업을 수행하는 방법을 기억하는 데 도움을 주는 데 사용됩니다.

실제로 episodic memory는 종종 few-shot 예제 프롬프팅을 통해 구현되며, 여기서 agent는 과거 시퀀스에서 학습하여 작업을 올바르게 수행합니다. 때로는 "말하기"보다 "보여주기"가 더 쉽고, LLM은 예제로부터 잘 학습합니다. Few-shot learning을 사용하면 의도된 동작을 설명하는 입력-출력 예제로 프롬프트를 업데이트하여 LLM을 ["프로그래밍"](https://x.com/karpathy/status/1627366413840322562)할 수 있습니다. Few-shot 예제를 생성하는 데 다양한 모범 사례를 사용할 수 있지만, 종종 어려움은 사용자 입력을 기반으로 가장 관련성 있는 예제를 선택하는 데 있습니다.




메모리 [store](/oss/python/langgraph/persistence#memory-store)는 few-shot 예제로 데이터를 저장하는 한 가지 방법일 뿐입니다. 더 많은 개발자 참여를 원하거나 few-shot을 평가 도구와 더 긴밀하게 연결하려는 경우, [LangSmith Dataset](/langsmith/home-datasets-for-dynamic-few-shot-example-selection#dynamic-few-shot-example-selection)을 사용하여 데이터를 저장할 수도 있습니다. 그런 다음 동적 few-shot 예제 선택기를 즉시 사용하여 동일한 목표를 달성할 수 있습니다. LangSmith는 데이터셋을 인덱싱하고 키워드 유사성(키워드 기반 유사성을 위해 [BM25와 유사한 알고리즘 사용](/langsmith/home-datasets-for-dynamic-few-shot-example-selection#dynamic-few-shot-example-selection))을 기반으로 사용자 입력과 가장 관련성 있는 few-shot 예제의 검색을 가능하게 합니다.

LangSmith의 동적 few-shot 예제 선택의 예제 사용법은 이 [비디오](https://www.youtube.com/watch?v=37VaU7e7t5o)를 참조하세요. 또한 도구 호출 성능을 개선하기 위한 few-shot 프롬프팅을 보여주는 이 [블로그 포스트](https://blog.langchain.dev/few-shot-prompting-to-improve-tool-calling-performance/)와 LLM을 인간 선호도에 맞추기 위해 few-shot 예제를 사용하는 이 [블로그 포스트](https://blog.langchain.dev/aligning-llm-as-a-judge-with-human-preferences/)를 참조하세요.




#### Procedural memory

인간과 AI agent 모두에서 [Procedural memory](https://en.wikipedia.org/wiki/Procedural_memory)는 작업을 수행하는 데 사용되는 규칙을 기억하는 것을 포함합니다. 인간의 경우, procedural memory는 기본 운동 기술과 균형을 통해 자전거를 타는 것과 같은 작업을 수행하는 방법에 대한 내재화된 지식과 같습니다. 반면 episodic memory는 보조 바퀴 없이 처음으로 자전거를 성공적으로 탄 경험이나 경치 좋은 경로를 통한 기억에 남는 자전거 타기와 같은 특정 경험을 회상하는 것을 포함합니다. AI agent의 경우, procedural memory는 모델 가중치, agent 코드, agent의 프롬프트의 조합으로 agent의 기능을 집합적으로 결정합니다.

실제로 agent가 모델 가중치를 수정하거나 코드를 다시 작성하는 것은 상당히 드뭅니다. 그러나 agent가 자체 프롬프트를 수정하는 것은 더 일반적입니다.

Agent의 지침을 개선하는 한 가지 효과적인 접근 방식은 ["Reflection"](https://blog.langchain.dev/reflection-agents/) 또는 메타 프롬프팅을 통하는 것입니다. 이는 agent에게 현재 지침(예: 시스템 프롬프트)과 최근 대화 또는 명시적 사용자 피드백을 함께 프롬프팅하는 것을 포함합니다. 그런 다음 agent는 이 입력을 기반으로 자체 지침을 개선합니다. 이 방법은 지침을 미리 지정하기 어려운 작업에 특히 유용하며, agent가 상호작용으로부터 학습하고 적응할 수 있게 해줍니다.

예를 들어, 우리는 외부 피드백과 프롬프트 재작성을 사용하여 Twitter용 고품질 논문 요약을 생성하는 [Tweet 생성기](https://www.youtube.com/watch?v=Vn8A3BxfplE)를 구축했습니다. 이 경우 특정 요약 프롬프트를 *사전에* 지정하기 어려웠지만, 사용자가 생성된 Tweet을 비판하고 요약 프로세스를 개선하는 방법에 대한 피드백을 제공하는 것은 상당히 쉬웠습니다.

아래 의사 코드는 LangGraph 메모리 [store](/oss/python/langgraph/persistence#memory-store)로 이를 구현하는 방법을 보여줍니다. store를 사용하여 프롬프트를 저장하고, `update_instructions` 노드가 현재 프롬프트(`state["messages"]`에 캡처된 사용자와의 대화에서 피드백도 함께)를 가져오고, 프롬프트를 업데이트하고, 새 프롬프트를 store에 다시 저장합니다. 그런 다음 `call_model`이 store에서 업데이트된 프롬프트를 가져와 응답을 생성하는 데 사용합니다.

```python
# Node that *uses* the instructions
def call_model(state: State, store: BaseStore):
    namespace = ("agent_instructions", )
    instructions = store.get(namespace, key="agent_a")[0]
    # Application logic
    prompt = prompt_template.format(instructions=instructions.value["instructions"])
    ...

# Node that updates instructions
def update_instructions(state: State, store: BaseStore):
    namespace = ("instructions",)
    instructions = store.search(namespace)[0]
    # Memory logic
    prompt = prompt_template.format(instructions=instructions.value["instructions"], conversation=state["messages"])
    output = llm.invoke(prompt)
    new_instructions = output['new_instructions']
    store.put(("agent_instructions",), "agent_a", {"instructions": new_instructions})
    ...
```

### Writing memories

Agent가 메모리를 작성하는 두 가지 주요 방법이 있습니다: ["hot path에서"](#in-the-hot-path)와 ["백그라운드에서"](#in-the-background).

![](/oss/images/hot_path_vs_background.png)

#### In the hot path

런타임 중에 메모리를 생성하는 것은 장점과 과제를 모두 제공합니다. 긍정적인 측면에서, 이 접근 방식은 실시간 업데이트를 가능하게 하여 새로운 메모리를 후속 상호작용에서 즉시 사용할 수 있게 합니다. 또한 투명성을 가능하게 하여 메모리가 생성되고 저장될 때 사용자에게 알릴 수 있습니다.

그러나 이 방법은 또한 과제를 제시합니다. Agent가 메모리에 커밋할 것을 결정하기 위해 새로운 도구가 필요한 경우 복잡성이 증가할 수 있습니다. 또한 메모리에 저장할 것에 대해 추론하는 프로세스가 agent 지연 시간에 영향을 미칠 수 있습니다. 마지막으로, agent는 메모리 생성과 다른 책임 사이에서 멀티태스킹해야 하며, 이는 생성된 메모리의 양과 품질에 잠재적으로 영향을 미칠 수 있습니다.

예를 들어, ChatGPT는 [save_memories](https://openai.com/index/memory-and-new-controls-for-chatgpt/) 도구를 사용하여 메모리를 콘텐츠 문자열로 upsert하며, 각 사용자 메시지와 함께 이 도구를 사용할지 여부와 방법을 결정합니다. 참조 구현으로 우리의 [memory-agent](https://github.com/langchain-ai/memory-agent) 템플릿을 참조하세요.

#### In the background

별도의 백그라운드 작업으로 메모리를 생성하는 것은 여러 가지 이점을 제공합니다. 기본 애플리케이션의 지연 시간을 제거하고, 애플리케이션 로직을 메모리 관리와 분리하며, agent가 더 집중된 작업 완료를 할 수 있게 해줍니다. 이 접근 방식은 또한 중복 작업을 피하기 위해 메모리 생성 시점을 유연하게 조정할 수 있습니다.

그러나 이 방법에는 고유한 과제가 있습니다. 메모리 작성 빈도를 결정하는 것이 중요해지며, 업데이트가 자주 이루어지지 않으면 다른 thread에 새 context가 없을 수 있습니다. 메모리 형성을 트리거할 시점을 결정하는 것도 중요합니다. 일반적인 전략으로는 설정된 기간 후 예약(새 이벤트가 발생하면 재예약), cron 일정 사용 또는 사용자나 애플리케이션 로직에 의한 수동 트리거 허용이 있습니다.

참조 구현으로 우리의 [memory-service](https://github.com/langchain-ai/memory-template) 템플릿을 참조하세요.

### Memory storage

LangGraph는 장기 메모리를 [store](/oss/python/langgraph/persistence#memory-store)의 JSON 문서로 저장합니다. 각 메모리는 사용자 정의 `namespace`(폴더와 유사)와 고유한 `key`(파일 이름과 유사) 아래에 구성됩니다. Namespace는 종종 정보를 더 쉽게 구성할 수 있도록 사용자 또는 조직 ID나 다른 레이블을 포함합니다. 이 구조는 메모리의 계층적 구성을 가능하게 합니다. 그런 다음 콘텐츠 필터를 통해 namespace 간 검색이 지원됩니다.

```python
from langgraph.store.memory import InMemoryStore


def embed(texts: list[str]) -> list[list[float]]:
    # Replace with an actual embedding function or LangChain embeddings object
    return [[1.0, 2.0] * len(texts)]


# InMemoryStore saves data to an in-memory dictionary. Use a DB-backed store in production use.
store = InMemoryStore(index={"embed": embed, "dims": 2})
user_id = "my-user"
application_context = "chitchat"
namespace = (user_id, application_context)
store.put(
    namespace,
    "a-memory",
    {
        "rules": [
            "User likes short, direct language",
            "User only speaks English & python",
        ],
        "my-key": "my-value",
    },
)
# get the "memory" by ID
item = store.get(namespace, "a-memory")
# search for "memories" within this namespace, filtering on content equivalence, sorted by vector similarity
items = store.search(
    namespace, filter={"my-key": "my-value"}, query="language preferences"
)
```




메모리 store에 대한 자세한 내용은 [Persistence](/oss/python/langgraph/persistence#memory-store) 가이드를 참조하세요.
