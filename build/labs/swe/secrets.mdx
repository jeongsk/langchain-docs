Open-SWE는 사용자 환경 변수를 에이전트와 안전하게 공유하고 개발 서버에 전달하기 위해 암호화된 방식을 구현합니다.

## 환경 변수 및 API 키

### API 키 보호 방식

API 키는 전송 중과 저장 시 모두 업계 표준인 AES-256-GCM 암호화로 보호됩니다.

**저장 프로세스:**
1. **프론트엔드**: 브라우저 localStorage에 임시로 저장 (평문)
2. **전송**: 백엔드로 전송하기 전에 AES-256-GCM으로 암호화
3. **백엔드**: LangGraph 데이터베이스에 암호화되어 저장
4. **런타임**: 서버 측 암호화 키를 사용하여 필요 시 복호화

<Accordion title="기술적 암호화 세부사항">
  **암호화 세부사항:**
  - **알고리즘**: [AES-256-GCM](https://nvlpubs.nist.gov/nistpubs/Legacy/SP/nistspecialpublication800-38d.pdf) (인증된 암호화)
  - **키 유도**: 시스템 `SECRETS_ENCRYPTION_KEY`의 SHA-256 해시
  - **IV 생성**: 암호화마다 무작위 12바이트 초기화 벡터
  - **인증**: 16바이트 인증 태그로 변조 방지
</Accordion>

### 시스템 환경 변수 vs 사용자 환경 변수

Open-SWE는 두 가지 유형의 환경 변수를 처리합니다:

**시스템 환경 변수:**
- **용도**: Open-SWE 실행에 필요한 환경 변수입니다. 자체 호스팅하는 경우 LLM, 인프라, 인증 키를 설정할 수 있습니다
- **예시**: `DAYTONA_API_KEY`, `SECRETS_ENCRYPTION_KEY`, `GITHUB_APP_PRIVATE_KEY`
- **접근**: `process.env`를 통한 서버 측 전용
- **보안**: 사용자나 샌드박스에 절대 노출되지 않음

**사용자 정의 환경 변수:**
- **용도**: 개인 API 키 및 커스텀 개발 변수
- **예시**: `ANTHROPIC_API_KEY`, `MY_DATABASE_URL`, `STRIPE_TEST_KEY`
- **접근**: UI의 설정 페이지를 통해 사용자가 제어
- **보안**: AES-256-GCM 암호화 + 개발 서버로 전달하기 위해 명시적인 사용자 동의 필요

### API 키가 샌드박스 환경에 노출되는 경우

API 키는 샌드박스 환경에 **절대 자동으로 노출되지 않습니다**. 노출에는 명시적인 사용자 동의가 필요합니다.

샌드박스 환경에 왜 API 키가 필요한지 궁금할 수 있습니다. 저희는 Open-SWE를 여러분의 주니어 개발자로 설계했습니다. 개발의 일부는 실시간으로 코드를 테스트하는 것입니다. **Open-SWE는 실행 중인 샌드박스 내에서 LangGraph 에이전트, Next.js 앱, Flask 서버 등을 실행할 수 있는 개발 서버를 시작할 수 있는 기능을 가지고 있습니다.** 이 옵션이 유용하다고 생각되면, 키를 샌드박스에 전달하는 것의 의미를 검토해 주시기 바랍니다.

<Note>
  샌드박스 접근을 활성화할 때는 프로덕션 키 대신 제한된 권한을 가진 별도의 개발 API 키를 사용하는 것을 고려하세요. 이렇게 하면 기능을 유지하면서 잠재적 노출의 영향을 줄일 수 있습니다.
</Note>

**기본 동작 (보안):**
- API 키는 LLM 모델 초기화 및 사용자가 전달한 경우 자체 키를 사용한 Daytona 설정에만 사용됩니다
- 키는 샌드박스에서 환경 변수로 사용할 수 없으며 LLM도 접근할 수 없습니다
- 각 키는 기본적으로 `allowedInDev: false`로 설정됩니다

**"개발 서버에 포함"을 활성화하는 경우:**
- 각 API 키에 대해 스위치를 수동으로 토글합니다
- 키가 샌드박스에서 환경 변수로 사용 가능해집니다
- 어떤 키가 노출될지 제어권을 유지합니다

## 샌드박스 보안 및 격리

### 컨테이너 격리

각 사용자 세션은 여러 보안 경계를 가진 완전히 격리된 Daytona 컨테이너에서 실행됩니다. 이러한 컨테이너는 새 브랜치의 저장소 코드를 수정할 수 있으며 세션 간에 정보를 교환하지 않습니다.

<Accordion title="격리 세부사항">
  **컨테이너 격리:**
  - 사용자 세션마다 별도의 컨테이너
  - 컨테이너 간 파일 시스템 공유 없음
  - 컨테이너 수준의 리소스 제한 및 할당량

  **프로세스 격리:**
  - 사용자 환경 변수 vs 시스템 환경 변수
  - 샌드박스 프로세스는 호스트 시스템이나 코드에 접근할 수 없음

  **시간적 격리:**
  - 15분간 비활성 후 자동 삭제
  - 세션 간 영구 저장소 없음
  - 각 새 세션마다 새로운 환경

  **네트워크 격리:**
  - 컨테이너 간 통신 불가
</Accordion>

## 데이터 처리 및 접근 제어

<Warning>
  API 키에 대해 "개발 서버에 포함"을 활성화하면 자격 증명의 공격 표면이 확장됩니다. AI 에이전트가 생성된 코드나 로그에서 환경 변수를 실수로 노출할 수 있습니다. 개발 서버 모니터링에 필요한 경우에만 이 기능을 사용하세요.
</Warning>

### 개발 환경 노출 위험

개발 서버 모니터링에 유용하다고 판단되는 경우에만 이 기능을 사용해야 합니다. 주요 키를 사용하지 말고 샌드박스 환경에 전달하는 키에 대한 접근 제어를 설정하는 것을 권장합니다.

Open-SWE UI와 에이전트는 암호화를 사용하여 이를 교환하지만, **LLM이 코드에서 환경 변수를 노출된 상태로 남겨둘 수 있습니다.**

## 보안 모범 사례

저희 팀은 내부적으로 Open-SWE를 애용하고 있으며 다음과 같은 모범 사례를 권장합니다:

- 각 API 키에 필요한 최소 권한만 사용하세요
- API 키를 정기적으로 교체하세요
- 특정 도구에 필요한 경우에만 "개발 서버에 포함"을 활성화하세요
- 설정에서 "마지막 사용" 타임스탬프를 모니터링하세요
- 샌드박스 환경에는 프로덕션 키 대신 별도의 개발 키 사용을 고려하세요
- 프로덕션 데이터베이스 자격 증명이나 높은 권한의 API 키에는 절대 샌드박스 접근을 활성화하지 마세요
- 배포하기 전에 생성된 코드에서 실수로 노출된 환경 변수가 없는지 검토하세요
