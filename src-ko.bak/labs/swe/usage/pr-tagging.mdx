</Warning>

# PR 태깅 통합

Open SWE는 풀 리퀘스트 상호작용에서 에이전트를 태깅하여 자동화된 실행을 직접 트리거할 수 있도록 지원합니다. 이 기능을 통해 GitHub 인터페이스를 벗어나지 않고도 코드 변경을 요청하거나, 질문하거나, 리뷰 피드백을 해결할 수 있는 원활한 방법을 제공합니다.

## PR 태깅 작동 방식

다음 컨텍스트 중 하나에서 `@open-swe`를 멘션하여 Open SWE를 트리거할 수 있습니다:

### PR 리뷰
- 풀 리퀘스트에 **리뷰를 남기고** 리뷰 본문에 `@open-swe`를 태깅합니다
- Open SWE가 전체 리뷰를 처리하고 그 안의 모든 댓글을 해결합니다
- 여러 변경이 필요한 종합적인 피드백에 이상적입니다

### 리뷰 댓글
- 특정 라인별 리뷰 댓글에서 **`@open-swe`를 태깅**합니다
- Open SWE가 해당 특정 댓글을 해결하는 데 집중합니다
- 특정 코드 섹션에 대한 타겟팅된 수정에 완벽합니다

### 일반 PR 댓글
- **PR에 댓글을 달고** `@open-swe`를 태깅하여 일반적인 변경을 요청합니다
- Open SWE가 요청된 수정 사항을 구현합니다
- 더 광범위한 변경이나 새로운 기능 요청에 가장 적합합니다

<Note>
  `@open-swe`를 태깅할 때마다 **새로운 독립적인 실행**이 생성됩니다. 동일한 댓글이나 서로 다른 댓글에 여러 개의 태그가 있으면 별도의 실행이 각각 실행됩니다.
</Note>

## 컨텍스트 및 보안 고려사항

<Warning>
  **보안 알림**: PR에서 Open SWE를 태깅하면 해당 풀 리퀘스트의 **모든 댓글, 리뷰, 리뷰 댓글**과 연결된 이슈에 접근할 수 있습니다. 잠재적인 프롬프트 인젝션 공격을 인지하고 이 기능을 사용할 때 PR 토론이나 연결된 이슈에 민감한 정보를 포함하지 않도록 주의하세요.
</Warning>

### 포함되는 컨텍스트

Open SWE가 PR 태깅 요청을 처리할 때 다음을 자동으로 수집합니다:

- **모든 PR 댓글** (일반 토론 댓글)
- **모든 리뷰** (관련 리뷰 댓글 포함)
- **모든 리뷰 댓글** (라인별 피드백)
- **연결된 이슈** (PR 설명에서 참조됨, 이슈 제목과 설명)

### 연결된 이슈 감지

Open SWE는 PR 설명에서 다음 키워드를 사용하여 연결된 이슈를 자동으로 감지하고 포함합니다:
- `fixes #123` 또는 `fix #123`
- `closes #456` 또는 `close #456`
- `resolves #789` 또는 `resolve #789`

이러한 패턴이 발견되면 Open SWE는 요구사항을 더 잘 이해하기 위한 추가 컨텍스트로 이슈 제목과 설명을 포함합니다.

## Open SWE 응답 방식

Open SWE는 요청에 따라 **코드 변경**과 **질문** 모두를 처리할 수 있습니다:

### 코드 변경
코드 수정을 요청하면 Open SWE는 다음을 수행합니다:
1. 원본 PR 브랜치를 가리키는 **새 브랜치를 생성**합니다
2. 이 새 브랜치에서 **요청된 변경 사항을 구현**합니다
3. 변경 사항이 포함된 **새 풀 리퀘스트를 생성**합니다
4. 쉬운 리뷰를 위해 **새 PR을 원본 PR에 연결**합니다

이 워크플로우는 원본 PR을 변경하지 않은 상태로 유지하면서 제안된 수정 사항을 별도로 리뷰할 수 있도록 합니다.

### 질문 및 조사
Open SWE는 코드 변경이 필요하지 않은 질문에도 응답할 수 있습니다:
- 코드 기능이나 아키텍처 결정에 대해 질문합니다
- 기존 구현에 대한 설명을 요청합니다
- 대안적 접근 방식에 대한 제안을 받습니다

### 댓글 위치별 응답 유형

**리뷰 댓글 (라인별)**
- Open SWE가 **리뷰 댓글에 직접 답변**합니다
- 응답이 동일한 대화 스레드에 나타납니다

**리뷰 메시지 (전체 리뷰)**
- Open SWE가 PR에 **새 댓글을 생성**합니다
- 원본 리뷰를 인용하고 리뷰어를 태깅합니다
- 리뷰에 대한 종합적인 응답을 제공합니다

**일반 PR 댓글**
- Open SWE가 PR에 **새 댓글을 생성**합니다
- 원본 댓글을 인용하고 댓글 작성자를 태깅합니다
- 특정 요청이나 질문을 처리합니다

## 시작하기

PR 태깅을 사용하려면:

1. **리포지토리에 대해 Open SWE가 올바르게 구성되었는지 확인**합니다 (아래 자체 호스팅 섹션 참조)
2. Open SWE가 설치된 리포지토리의 **임의의 풀 리퀘스트로 이동**합니다
3. 원하는 내용을 설명하는 **댓글, 리뷰 또는 리뷰 댓글을 남깁니다**
4. 메시지 어디에나 **`@open-swe`를 태깅**합니다
5. **Open SWE의 응답을 기다립니다** - 즉시 답변하고 처리를 시작합니다

### 사용 예시

```markdown
@open-swe 이 함수를 프로미스 대신 async/await를 사용하도록 리팩토링해줄 수 있나요?
```

```markdown
전반적으로 이 코드는 좋아 보이지만, 더 나은 에러 처리가 필요할 것 같습니다.
@open-swe try-catch 블록과 적절한 에러 로깅을 추가해주세요.
```

```markdown
@open-swe 이전 구현과 비교했을 때 이 접근 방식의 성능 영향은 어떤가요?
```

## 자체 호스팅 구성

자체 호스팅 Open SWE 인스턴스에서 PR 태깅을 사용하려면 커스텀 트리거 사용자 이름을 구성해야 합니다:

### 1단계: GitHub 사용자 계정 생성

태깅 트리거로 사용될 전용 GitHub 사용자 계정을 생성합니다:
- 기억하기 쉬운 사용자 이름을 선택합니다 (예: GitHub App 이름과 일치)
- 이 계정은 특별한 권한이 필요하지 않으며 태깅용으로만 사용됩니다

### 2단계: 트리거 함수 업데이트

`apps/open-swe/src/routes/github/utils.ts`에서 `mentionsGitHubUserForTrigger` 함수를 수정합니다:

```typescript
export function mentionsGitHubUserForTrigger(commentBody: string): boolean {
  return /@your-custom-username\b/.test(commentBody);
}
```

`your-custom-username`을 생성한 GitHub 사용자 이름으로 교체합니다.

### 3단계: 환경 변수 설정

`apps/open-swe/.env`의 환경 구성에 트리거 사용자 이름을 추가합니다:

```bash
GITHUB_TRIGGER_USERNAME="your-custom-username"
```

이것은 1단계의 사용자 이름과 일치해야 합니다 (@ 기호 제외).

### 4단계: 허용된 사용자 업데이트

실행을 트리거할 수 있도록 허용된 GitHub 사용자 이름을 에이전트의 배포 환경에 있는 `NEXT_PUBLIC_ALLOWED_USERS_LIST` 환경 변수에 추가합니다 (허용된 사용자 기능을 활용하려면 웹 앱과 에이전트 모두의 프로덕션 배포에 포함하세요).

```bash
NEXT_PUBLIC_ALLOWED_USERS_LIST='["your-github-username", "teammate-username"]'
```

로컬에서 실행할 때는 모든 사용자가 "허용된 사용자"입니다. 웹 앱의 프로덕션 환경 변수에도 이 환경 변수를 설정하는 것이 좋습니다. 그러면 사용자가 웹 앱을 통해 Open SWE를 호출할 때 자체 API 키를 설정할 필요가 없습니다.

<Tip>
  이러한 구성 변경을 수행한 후 새 설정이 적용되도록 Open SWE 인스턴스를 재시작하세요. 그런 다음 PR 댓글에서 커스텀 사용자 이름을 태깅하여 기능을 테스트할 수 있습니다.
</Tip>

## 모범 사례

- **구체적으로 요청**하여 더 나은 결과를 얻으세요
- **다른 유형의 변경에는 별도의 태그를 사용**하여 실행을 집중적으로 유지하세요
- 품질을 보장하기 위해 **생성된 PR을 머지하기 전에 리뷰**하세요
- **컨텍스트를 염두에 두세요** - PR 토론에서 민감한 정보를 피하세요
- 자체 호스팅을 설정할 때 **간단한 요청으로 먼저 테스트**하세요

## 문제 해결

PR 태깅이 작동하지 않는 경우:

1. **GitHub App 권한 확인** - 필요한 이벤트 구독이 활성화되어 있는지 확인합니다
2. **환경 변수 검증** - `GITHUB_TRIGGER_USERNAME`이 올바르게 설정되어 있는지 확인합니다
3. **허용된 사용자 검토** - GitHub 사용자 이름이 `ALLOWED_USERS` 목록에 있는지 확인합니다
4. **웹훅 구성 확인** - 웹훅이 올바르게 구성되어 있고 이벤트를 수신하고 있는지 확인합니다
5. **로그 모니터링** - 오류 메시지나 디버깅 정보에 대해 Open SWE 로그를 확인합니다

추가 도움이 필요하면 [개발 설정 가이드](/labs/swe/setup/development)를 참조하거나 문제 해결 리소스에 대한 GitHub 리포지토리를 확인하세요.
